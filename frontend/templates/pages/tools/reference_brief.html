Read the brief as a decision, not a screenshot description

A useful reference has a job. It might explain how a headline and product view work together, how a pricing unit stays attached to an amount, or how a form introduces an error. Start with that job rather than asking a coding agent to reproduce an entire page. You are selecting a principle for your own product, not approving another site's assets, prices or behavior.

The builder keeps the observation, decision and implementation requirement separate. That separation matters when someone asks why the design changed: the source may show a useful relationship, while your product needs different content, controls or limits. The exported notes are quoted as supplied material. They do not override the agent's project instructions or establish that a linked page is trustworthy.

Choose borrow, adapt or reject

Borrow means keeping a named principle, such as putting an explanation next to the value it qualifies. State what stays consistent, and describe it in your own project's terms. Do not turn “borrow” into an instruction to download another company's illustration or reuse its copy.

Adapt needs an intentional difference. For the example above, the proximity of amount and billing unit is useful, but a per-teammate label would be wrong for an agency-priced product. Record both the relationship to retain and the change to make. If you cannot name the difference, inspect the reference again before choosing this option.

Reject creates a boundary. A dramatic hover effect may look appealing but hide information that your mobile visitors need immediately. Name the pattern the implementation must leave out and the reason. Then specify what the page should do instead. A rejection without an alternative leaves the next person to guess.

A worked adaptation

Evidence: a hypothetical desktop sketch puts the billed unit below the price. Decision: retain that relationship, replace the unit with the approved agency unit, and reject copied allowance claims. Requirement: show the actual unit beside each amount. Unknown: the limit policy still needs a product decision. This is a completed reasoning example, not a tested pricing page.

Keep evidence and unknowns attached

Record the reference URL and, when available, its catalogue ID, capture date, width and visible state. A desktop image does not show what happens at a narrow viewport, after a click, with a keyboard or during an error. Write those limits in the evidence context rather than quietly turning them into assumptions.

Optional fields left blank export as “Not recorded — confirm before implementation.” The builder does not supply missing customer research, brand rules, layout measurements or source verification. It does not rank references or choose a library. Use the coding-agent briefing guide for the broader observation and handoff workflow, or choose pricing references by buying decision when the offer is the hard part.

Write a check someone can actually run

Give the browser task an action, an inspection condition and an expected result. “Looks good on mobile” is not repeatable. “At 390 px, locate the billing unit beside each amount without opening a tooltip” gives the reviewer something to do. Add keyboard, zoom, long-content or failure states when they matter to this specific decision.

A brief is not a passing test

Every exported acceptance task begins NOT CHECKED. After implementation, run it in the actual project and record the observed behavior and evidence. If the source or the result could not be inspected, leave that part unresolved. A filled form cannot establish accessibility, responsive correctness or conversion performance.

How the builder works

Reviewed November 17, 2026. The builder assembles your entries into Markdown in your browser. It makes no source-fetching or AI-generation request and does not save entries to browser storage or create a result URL. Copy and download operate on the current built brief; editing a field clears that result until you build it again. Ordinary site assets and navigation still use the network.

Copy or download before leaving: refreshing the page starts over with the example. URLs must use HTTP or HTTPS without credentials, a query or a fragment; keep reference IDs in the context field. Fields are limited to 2,000 characters. Missing required notes or an invalid URL prevent export. Review what you share with another person or service, and leave credentials and private customer information out.

Common questions

Does it analyze a URL or screenshot?

No. You inspect the source and enter the observations. For a starting point, explore public design references and choose one for a specific job. TastefulKit's available screenshots and DESIGN.md guides are references, not downloadable component source or permission to copy third-party assets.

Can I brief more than one reference?

Build one decision at a time, then combine the exported sections in your project document. Give each source a distinct job and resolve conflicts explicitly. The builder does not decide which reference wins when their directions disagree.

What if copying or downloading fails?

The generated Markdown remains selectable. Copy it manually from the result field. If JavaScript is unavailable, use the written worksheet in the briefing guide; no source inspection or browser test is claimed in either path.
